## 反思 SPA，混合渲染时代

大家发现：**不是所有网站都适合纯 SPA**

## CSR 客户端（浏览器）渲染（传统 SPA，Vue/React 原生）

**渲染时机：用户浏览器里**

1. 浏览器下载空 HTML + js 包
2. JS 下载并执行，在浏览器生成页面 DOM
3. 页面才展示出来

✅ 优点：页面切换快，交互流畅

❌ 缺点：首屏白屏；爬虫看不到真实内容，SEO 差




## SSR / SSG / ISR 服务端渲染方案
三个是**页面渲染时机**的方案，核心解决 SPA（单页应用）首屏白屏、SEO 差的问题。



## 1） SSR 服务端渲染（Server-Side Rendering）

**渲染时机：【每次访问】都在服务端实时生成 HTML**

流程：

1. 用户请求页面 → 服务端运行组件，请求接口数据
2. 服务端**一次性生成完整 HTML**返回给浏览器
3. 浏览器直接展示 HTML，之后 JS 注水（hydrate），页面变成可交互

✅ 优点

- 首屏快，爬虫拿到完整 HTML，SEO 友好
- 每次请求拿到**最新实时数据**

❌ 缺点

- **每次访问都要执行渲染 + 查接口，服务器压力大**
- 有服务耗时，并发高的时候页面会慢

> Next App Router / Nuxt 都支持 SSR。Nuxt 默认就是 SSR；Next Pages Router 可以开启 SSR，App Router Server Component 本质也是服务端渲染。

> 适用：后台大盘、实时资讯、需要实时数据的页面（订单、用户中心）

## 2） SSG 静态站点生成（Static Site Generation，预渲染）

**渲染时机：【项目打包构建的时候一次性生成全部 HTML】**

构建阶段就跑组件、拉取数据，把所有页面 HTML 一次性生成，产物就是一堆静态 html 文件。用户访问时直接返回静态文件，**不再跑服务端代码**。

✅ 优点

- 访问速度极快，CDN 友好，服务器压力几乎为 0
- SEO 最好
    
    ❌ 缺点
- **构建之后内容固定，不自动更新**，改数据必须重新打包部署
- 如果页面数量巨大，打包会非常慢

> Next：`getStaticProps`（Pages）；App Router 里静态页面默认就是 SSG
> 
> Nuxt：`nuxt generate` 打包产出静态页面

适用：官网、营销页、文档、博客，内容不频繁变动


## 3） ISR 增量静态再生（Incremental Static Regeneration）

> Next 最先推出，Nuxt3 也支持。**SSG + SSR 的折中方案**
> 
> **渲染时机：构建时预生成；之后在指定间隔内，后台自动重新生成页面**
> 
> 流程：

1. 打包的时候，预先生成一部分页面静态 HTML
2. 用户访问页面：直接返回缓存好的静态页面（快）
3. 当命中过期时间（如 revalidate:60），下一次访问时**后台异步重新拉数据、重新生成静态页面，更新缓存**

> 用户不会等待重新生成，旧缓存先返回

✅ 优点

- 大部分请求走静态缓存，速度接近 SSG
- 不需要全量重新打包，页面可以自动更新内容
    
    ❌ 缺点
- 更新不是实时，会有最多等于 revalidate 时间的延迟
- 存在缓存，强实时场景不适合





# 📊 对比汇总

|模式|渲染发生时间|数据新鲜度|性能|服务器开销|SEO|
|---|---|---|---|---|---|
|CSR|用户浏览器|实时|首屏差，跳转快|极低|❌差|
|SSR|**每次请求，服务端实时渲染**|实时|首屏较好|高|✅好|
|SSG|**打包构建一次性预渲染**|构建那一刻固定|极好|几乎 0|✅极好|
|ISR|构建预生成 + 后台定时增量更新|准实时（有缓存延迟）|极好|低||
