**不开虚拟滚动，单纯滚动 `overflow:auto` 容器：默认不会触发重排（reflow），一定会触发重绘（repaint）。**

> 重排 = 重新计算元素尺寸 / 位置；重绘 = 重新画像素；合成 = GPU 移动图层。

## 原理拆解（非虚拟滚动，普通长列表 / 普通表格）

容器 `overflow: auto`，里面一次性渲染全部 DOM，行都是正常文档流元素。

1. **滚动只是视口裁切，所有元素的几何大小、top/left 完全没变**
    
    - 元素宽高、位置没有改动 → **不需要重排 reflow**
    
2. 但元素一部分滚出视口、一部分进入视口，像素画面变了
    
    - 浏览器需要重新绘制可见区域 → **触发重绘 repaint**
    - 默认情况下，**重绘区域是整个滚动容器**（不是只画新增进来那一行）
    

> ✅一句话：普通表格不开虚拟滚动滚动时：**无 reflow，有 repaint**

## 但是！有几个例外，滚动时会触发重排（这是坑）

只要下面任意一种情况，滚动过程就会产生 reflow，INP 飙升：

1. **JS 滚动回调里读取布局属性**
    
    `offsetTop / offsetHeight / clientWidth / getBoundingClientRect`
    
    浏览器为拿到最新布局，会**强制同步布局 Layout Thrashing，触发重排**。哪怕你只是读，没有修改 DOM。

js

```
container.addEventListener('scroll', ()=>{
  // ❌ 读布局，强制reflow
  const top = rowDom.offsetTop
})
```

2. **滚动回调里修改几何属性**
    
    修改 width /height/margin /top/left，会触发 reflow + repaint。
    
3. **容器内有固定定位 /sticky 粘性定位元素**
    
    滚动时 sticky 需要不断计算元素位置，**会持续触发 reflow**。
    

> 表格表头用`position:sticky`冻结，就是典型场景！普通表格不开虚拟滚动，滚动时表头 sticky 持续计算，**持续重排**，大数据下 INP 爆炸。

4. 有 CSS 属性会在滚动时触发布局：比如百分比高度依赖滚动容器

## 图层角度再对比

- 不开虚拟滚动普通表格：滚动 → **repaint**，整容器区域绘制；大量 DOM，绘制开销随 DOM 数量上升。DOM 越多，repaint 越慢，滚动卡顿。
- 开启虚拟滚动（AGGrid/vxe-table）：行用 transform 位移 + 独立合成层，滚动只触发**Composite 合成**，不重排、不重绘。

## 重点区分：普通表格不开虚拟滚动，卡顿根源是什么？

不是**重排**，而是：

1. DOM 数量巨大
2. 滚动触发**大面积重绘**，像素绘制耗时
3. 如果有 sticky 冻结列 / 冻结表头：滚动持续重排，雪上加霜
4. scroll 事件高频触发，回调内写了 DOM 读取，强制布局

## 快速对比表

| 场景                                    | 是否重排 reflow | 是否重绘 repaint      |
| ------------------------------------- | ----------- | ----------------- |
| 普通 overflow 容器，无 sticky，滚动无 JS 读写 DOM | ❌否          | ✅是                |
| 普通容器 + sticky 冻结表头                    | ✅是          | ✅是                |
| 滚动回调读取 offset/getBoundingClientRect   | ✅是          | ✅是                |
| 虚拟滚动表格（transform 行）                   | ❌否          | ❌否（仅合成 Composite） |
