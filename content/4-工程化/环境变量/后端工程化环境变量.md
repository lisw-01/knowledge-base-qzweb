> 核心一句话：**后端环境变量是【运行期注入】，进程启动时读入 `process.env`，改完重启即生效、不用重新构建；靠 `NODE_ENV` / `APP_ENV` 区分环境，配合 `.env` 文件本地化配置，敏感信息只存服务器/CI，绝不进代码库。**

## 一、后端 vs 前端：先对齐认知

| 对比项 | 前端（Vite） | 后端（Node） |
| --- | --- | --- |
| 注入时机 | 编译期（打包写死进 JS） | 运行期（进程启动时读入内存） |
| 读取方式 | `import.meta.env.XXX` | `process.env.XXX` |
| 前缀要求 | 必须 `VITE_` 等 | **无前缀要求**，任意命名 |
| 环境区分 | `--mode` 匹配 `.env.[mode]` | `NODE_ENV` / `APP_ENV` + 手动指定 env 文件 |
| 修改后 | 必须重新打包 | **重启进程即生效** |
| 安全性 | 变量暴露给浏览器，禁止放密钥 | 变量只在服务端内存，可存放密钥（但仍不能进 git） |

## 二、环境变量文件规范（dotenv 系）

### 1. 文件命名（社区通用约定）

```
.env                # 所有环境公共变量（一般只放非敏感的默认值）
.env.local          # 本地私有，必须 .gitignore
.env.development    # 开发环境
.env.test           # 测试环境
.env.staging        # 预发环境
.env.production     # 生产环境（通常不入库，由运维在服务器维护）
```

> ⚠️ 与前端不同：**dotenv 不会自动按 NODE_ENV 加载对应文件**，默认只加载 `.env`，其他文件必须显式指定（见第三节）。

### 2. 文件内容示例

```bash
# .env.development
NODE_ENV=development
APP_PORT=3000
DB_HOST=localhost
DB_PORT=3306
DB_USER=root
DB_PWD=123456
REDIS_URL=redis://localhost:6379
LOG_LEVEL=debug

# .env.production
NODE_ENV=production
APP_PORT=8080
DB_HOST=rds-xxxx.mysql.rds.aliyuncs.com
DB_PWD=xxxxxxxx
LOG_LEVEL=info
```

### 3. .gitignore 安全红线

```gitignore
# .gitignore
node_modules
.env
.env.*
!.env.example
```

- 生产真实密钥**永远不进 git**，由运维通过服务器环境变量、部署平台（K8s Secret、Docker secrets、CI/CD 变量）注入。
- 仓库里只提交 **`.env.example`**（只有 key 没有 value），供新成员照抄：

```bash
# .env.example
NODE_ENV=development
APP_PORT=3000
DB_HOST=
DB_PWD=
```

## 三、加载与切换环境文件（核心，方式要全面）

### 方式 ① 原生 `node --env-file`（Node 20.6+，零依赖，推荐新项目）

```json
// package.json
{
  "scripts": {
    "start:dev": "node --env-file=.env.development src/app.js",
    "start:test": "node --env-file=.env.test src/app.js",
    "start:prod": "node --env-file=.env.production src/app.js"
  }
}
```

### 方式 ② dotenv + 手动指定路径（最通用）

```json
{
  "scripts": {
    "start:dev": "node -r dotenv/config src/app.js dotenv_config_path=.env.development",
    "start:test": "node -r dotenv/config src/app.js dotenv_config_path=.env.test"
  }
}
```

### 方式 ③ dotenv-cli（命令更简洁）

```bash
npm i -D dotenv-cli
```

```json
{
  "scripts": {
    "start:dev": "dotenv -e .env.development -- node src/app.js",
    "start:test": "dotenv -e .env.test -- node src/app.js",
    "start:prod": "dotenv -e .env.production -- node src/app.js"
  }
}
```

### 方式 ④ 代码内按 NODE_ENV 动态加载（单入口，自动匹配）

先在脚本里用 `cross-env` 设置 `NODE_ENV`：

```bash
npm i -D cross-env   # Windows 下 NODE_ENV=xxx 语法无效，必须用 cross-env
```

```json
{
  "scripts": {
    "dev": "cross-env NODE_ENV=development nodemon src/app.js",
    "start:test": "cross-env NODE_ENV=test node src/app.js",
    "start:prod": "cross-env NODE_ENV=production node src/app.js"
  }
}
```

```js
// src/env.js —— 环境文件加载统一收口
require('dotenv').config({
  path: path.resolve(__dirname, `../.env.${process.env.NODE_ENV || 'development'}`)
})
// 再兜底加载一份 .env（可选，公共变量）
require('dotenv').config({ path: path.resolve(__dirname, '../.env') }) // 不覆盖已存在的
```

> ⚠️ 顺序陷阱：dotenv 是**先到先得、不覆盖已存在的变量**。如果 `.env` 里有 `DB_HOST` 而 `.env.development` 也有，谁先 config() 谁生效。所以必须**环境专属文件在前，公共文件在后**。

### 方式 ⑤ 直接注入进程环境变量（不落盘，生产/容器最推荐）

```bash
# Linux 临时注入
APP_PORT=8080 DB_PWD=xxx node src/app.js

# systemd / pm2 ecosystem.config.js
module.exports = {
  apps: [{
    name: 'api',
    script: 'src/app.js',
    env_production: {
      NODE_ENV: 'production',
      DB_HOST: 'rds-xxxx',
      DB_PWD: 'xxxx'
    }
  }]
}

# Docker
docker run -e DB_PWD=xxx --env-file .env.production my-app

# K8s：从 Secret 注入容器环境变量（生产最佳实践）
```

## 四、代码中使用环境变量

### ① 直接读取

```js
const port = process.env.APP_PORT      // ⚠️ 永远是 string！
const dbPwd = process.env.DB_PWD
if (process.env.NODE_ENV === 'production') { ... }
```

注意：`process.env` 所有值都是**字符串**，布尔/数字要自己转换：

```js
const isProd = process.env.NODE_ENV === 'production'
const port = Number(process.env.APP_PORT) || 3000
```

### ② 集中收口 + 默认值（推荐，避免全项目到处 process.env）

```js
// src/config/index.js
module.exports = {
  env: process.env.NODE_ENV || 'development',
  port: Number(process.env.APP_PORT) || 3000,
  db: {
    host: process.env.DB_HOST || 'localhost',
    port: Number(process.env.DB_PORT) || 3306,
    user: process.env.DB_USER,
    password: process.env.DB_PWD
  },
  log: { level: process.env.LOG_LEVEL || 'info' }
}

// 业务代码只 import config
const config = require('../config')
app.listen(config.port)
```

### ③ 启动时校验（强烈推荐，防止漏配导致运行中才炸）

```bash
npm i zod
```

```js
// src/config/validate.js
const { z } = require('zod')

const EnvSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  APP_PORT: z.coerce.number().default(3000),
  DB_HOST: z.string().min(1, 'DB_HOST 不能为空'),
  DB_PWD: z.string().min(1, 'DB_PWD 不能为空')
})

const parsed = EnvSchema.safeParse(process.env)
if (!parsed.success) {
  console.error('❌ 环境变量校验失败：', parsed.error.flatten().fieldErrors)
  process.exit(1)   // 启动即失败，快速暴露问题
}

module.exports = parsed.data   // 类型安全、带默认值的 env 对象
```

> 校验库选型：`zod` / `joi` / `envalid` / NestJS 内置 `@nestjs/config` 的 `validate()` 都行，本质一样：**进程启动时校验，缺配置直接退出，不带病运行。**

## 五、框架层面的环境变量方案

### Express / Koa

无内置方案，自己组合：`dotenv` + `cross-env` + 配置收口模块（见第四节）。

### NestJS（内置 @nestjs/config）

```bash
npm i @nestjs/config
```

```ts
// app.module.ts
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      envFilePath: [`.env.${process.env.NODE_ENV}`, '.env'],  // 按序加载，先到先得
      validate: validateEnv  // 启动校验
    })
  ]
})
export class AppModule {}

// 业务中使用
constructor(private configService: ConfigService) {
  const dbHost = this.configService.get<string>('DB_HOST')
}
```

### TypeScript 项目

编译后运行目录变化，`.env` 相对路径容易失效，务必用 `path.resolve` 基于项目结构定位：

```ts
import path from 'path'
import dotenv from 'dotenv'
dotenv.config({ path: path.join(__dirname, '../../.env.development') })
```

## 六、重要实操注意事项

1. **改了 .env 必须重启服务**（和前端一样），nodemon 默认也不监听 env 文件，可加 `watch: [".env"]`。
2. **`NODE_ENV=production` 的隐藏行为**：Express/Koa 会启用生产优化、关闭详细报错；`npm i --production` 跳过 devDependencies。不要用它当业务环境开关，业务区分另设 `APP_ENV`（development/test/staging/prod）。
3. **Windows 兼容**：`NODE_ENV=xxx node app.js` 在 Windows 报错，一律用 `cross-env` 或 Node 20.6+ 的 `--env-file`。
4. **优先级铁律**：真实进程环境变量 > dotenv 文件。服务器上已 export 的变量不会被 .env 覆盖（dotenv 不覆盖已存在的 key）。
5. **安全红线**：
   - `.env` 文件不入 git，只提交 `.env.example`；
   - 生产密钥用 K8s Secret / 云密钥管理（KMS）/ CI 变量注入，不要写进镜像；
   - 日志中禁止打印完整 env 对象，防止密钥泄漏到日志平台；
   - 打印配置时对 `*PWD*`、`*SECRET*`、`*TOKEN*` 做脱敏。
6. **配置分层**：env 只放"随环境变化"的值（地址、密钥、开关），业务常量（分页上限、枚举）放普通 config 文件即可，不要什么都塞 env。

## 七、完整目录示例

```
项目根目录
├─ .env                    # 公共默认（可选）
├─ .env.development        # 本地开发
├─ .env.test               # 测试
├─ .env.staging            # 预发
├─ .env.example            # 只有 key 的模板，提交 git
├─ .gitignore              # 忽略 .env*
├─ package.json            # cross-env / dotenv-cli 脚本
└─ src
   ├─ env.js               # dotenv 加载收口
   ├─ config
   │  ├─ validate.js       # zod 启动校验
   │  └─ index.js          # 集中导出 config
   └─ app.js
```

## 八、一图选型速查

| 场景 | 方案 |
| --- | --- |
| 新项目、Node ≥ 20.6 | `node --env-file=.env.xxx`（零依赖） |
| 老项目、通用兼容 | `dotenv-cli` 或 `dotenv.config({ path })` 按 NODE_ENV 加载 |
| Windows 团队协作 | `cross-env NODE_ENV=xxx` |
| 生产部署 | 不落盘：pm2 env / Docker `-e` / K8s Secret 注入 |
| 大型项目 / NestJS | `@nestjs/config` 或 env 收口模块 + zod 启动校验 |
