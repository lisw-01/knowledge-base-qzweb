> 核心一句话：**LLM 本身没有记忆——每次调用都是"失忆重启"；所谓长期记忆，就是把重要信息存到模型外面（文件/数据库/向量库），下次提问时检索回来垫进上下文**。本质 = 存储 + 检索 + 拼装，和 [RAG](5-agent/Agent/link_RAG) 是同一套原理，只是"资料"换成了"对话中提炼的信息"。

## 一、为什么需要长期记忆（模型天生失忆）

LLM API 是**无状态**的：

```
第1轮：你叫什么？  → 我叫小明        （模型此刻"知道"你叫小明）
第2轮：我叫什么？  → 我不知道你在说什么 （上轮的 messages 没传，模型完全失忆）
```

- 模型唯一的"记忆"就是本次请求里的 [messages](5-agent/LLM/link_messages参数)——你不传，它就不知道
- 最朴素的解法：**每次都把全部历史对话塞进 messages** → 这就是"短期记忆"
- 但短期记忆有天花板：上下文窗口有限（再大也有上限）、Token 按量计费（历史越长越贵）、关键信息被淹没（100 轮闲聊后，模型早忘了你第 3 轮说过对花生过敏）

**长期记忆 = 超出上下文窗口限制，把"值得记的信息"持久化到模型外面，按需取回。**

## 二、长期记忆的本质就三步

不管什么框架什么花活，拆开全是这个循环：

```
① 写入(存)：什么时候记？记什么？      → 对话结束后/每轮异步，提取"值得记"的信息
② 检索(取)：用户提问时，找回哪些记忆？  → 和当前问题最相关的 topK 条
③ 拼装(用)：怎么放回上下文？          → 作为 system/资料块拼进 Prompt
```

> 短期记忆（messages）是"全都带着"；长期记忆是"挑相关的带着"。**从全量携带 → 按需检索，就是从短期到长期的全部跨越。**

## 三、四种实现方案（由浅入深）

### 方案 1：全量携带（伪长期记忆）

把所有历史原样塞 messages，超窗就报错/被截断。

- ✅ 零成本实现，信息无损
- ❌ 贵、有上限、几百轮后必然崩
- **定位：demo 可用，产品必挂**

### 方案 2：摘要压缩

放不下了，就让 LLM 把旧历史**压缩成一段摘要**，替换原始对话：

```
[前50轮对话] --LLM压缩--> "用户叫小明，花生过敏，之前咨询过退货政策（已解决）..."
之后每轮 messages = 摘要 + 最近10轮原文
```

- ✅ 实现简单，成本可控，保留对话脉络
- ❌ 有损：细节会丢（"对花生过敏"可能被摘要成"聊过饮食偏好"）；摘要质量靠 Prompt

### 方案 3：向量检索记忆（主流，= 对话版 RAG）

把对话中提炼的信息切片 → Embedding → 存进[向量库](5-agent/Agent/link_向量库)，提问时按相似度检索 topK 拼进 Prompt：

```
写入：每轮结束 → "用户说他对花生过敏" → embed → 向量库.add
读取：用户问"帮我推荐午餐" → embed → 向量库.search topK
     → 命中"花生过敏" → 拼进 Prompt → LLM 避开花生
```

- ✅ 窗口无限（库可以存几万条）、按需取回、成本稳定
- ❌ 检索可能漏（问"推荐午餐"未必能召回"花生过敏"——语义距离不够近）；要维护向量库
- **和 RAG 的唯一区别：RAG 入库的是"文档知识"，这里入库的是"对话中提炼的关于用户的信息"**

### 方案 4：结构化记忆（画像/事实卡片）

不走向量检索，让 LLM 主动**抽取成键值对/档案**，每轮全量注入（量小所以塞得下）：

```
user_profile = {
  "姓名": "小明",
  "过敏原": ["花生"],
  "偏好": "口味偏辣",
  "近期目标": "减脂"
}
```

- ✅ 精确、可人工编辑、永不漏关键事实
- ❌ 只适合"关于用户的稳定事实"，存不下海量事件；抽取和更新逻辑要自己写

> **实战常用组合拳：方案 2 + 3 + 4** —— 近期对话带原文（短期），远期历史压摘要（方案2），用户画像存卡片（方案4），事件/知识走向量库（方案3）。

## 四、两个关键设计问题

### 1. 什么时候写入？（写记忆本身也要花钱）

| 策略 | 做法 | 代价 |
| --- | --- | --- |
| 每轮都提取 | 每轮对话后跑一次"这段有值得记的吗" | 每轮多一次 LLM 调用 |
| 定时/轮次批量 | 每 10 轮总结一次增量记忆 | 便宜，但中途崩了会丢 |
| 会话结束总结 | 对话结束时一次性沉淀 | 最省，但跨会话中途无记忆 |

> 折中：简单场景"会话结束总结"就够；助手类产品用"每轮异步提取 + 去重合并"。

### 2. 怎么防止记垃圾 / 记重复？

- 提取时给标准："只记稳定事实、偏好、未完成事项，闲聊不记"
- 写入前先**检索一遍相似记忆**：相似度高的走"更新合并"，不重复 add（Mem0 等框架的核心逻辑就是这个：**先 search 再决定 add / update / delete**）

## 五、迷你 Demo：30 行手写长期记忆（方案 3）

```python
# mini_memory.py —— 向量检索式长期记忆
from mypackage import embed, chat   # embed: 文本→向量; chat: 调LLM
from link_向量库 import MiniVectorDB  # 复用手写的迷你向量库

memory = MiniVectorDB()

def remember(text: str):
    """写入：判断 + 去重（相似度高就跳过）"""
    if memory.search(text, top_k=1) and memory.search(text, top_k=1)[0]["score"] > 0.9:
        return                      # 已有几乎相同的记忆，不重复记
    memory.add([text])

def ask(question: str, history: list) -> str:
    """读取：检索相关记忆，拼进 system"""
    hits = memory.search(question, top_k=3)
    memory_block = "\n".join(f"- {h['text']}" for h in hits)
    system = f"你是用户的助手。已知关于用户的记忆：\n{memory_block}" if hits else "你是用户的助手。"
    messages = [{"role": "system", "content": system}] + history + \
               [{"role": "user", "content": question}]
    return chat(messages)

# ===== 用起来（跨会话也记得）=====
ask("我对花生过敏", history=[])
remember("用户对花生过敏")          # 实战中这步交给 LLM 自动判断提取
print(ask("帮我推荐个午餐", history=[]))
# 命中记忆"花生过敏" → 回答自动避开花生
```

看懂这个循环，Mem0、LangChain Memory 这些框架对你就不黑盒了——它们只是把"提取什么、怎么去重、怎么分层"做得更工程化。

## 六、工业界记忆方案一览

| 方案 | 思路 | 特点 |
| --- | --- | --- |
| **Mem0** | 每轮提取 + 向量检索 + 冲突时 update/delete | 目前最流行的独立记忆层，API 简单 |
| **Letta（原 MemGPT）** | 模型自己管理记忆：核心记忆常驻 + 归档记忆分页，Agent 能自己调用"翻记忆"工具 | 思路最接近操作系统"内存分页"，适合长任务 Agent |
| **LangChain Memory** | 各类记忆的统一接口（ConversationBuffer/Summary/VectorStore…） | 跟 LangChain 绑定，抽象层较厚 |
| **Zep / Graphiti** | 记忆存成时序知识图谱（谁-做了什么-何时），支持时间推理 | 强大但重，适合对时效关系有要求的场景 |
| 手写（本笔记方案） | 向量库 + 提取 Prompt | **学习原理首选**，小项目直接能用 |

## 七、避坑清单

1. **别什么都记**：垃圾记忆会污染检索结果——"记 100 条，不如记准 10 条"
2. **记忆也会过期**："用户在减肥"三个月后可能不成立了，重要记忆带时间戳，定期让 LLM 复核
3. **检索不到 ≠ 没存**：先打印 search 结果排查（同 [RAG](5-agent/Agent/link_RAG) 排查思路），问题多半在 Embedding 或查询太远
4. 关键事实（过敏、账号、约束）别只靠向量检索，**结构化卡片兜底**——检索漏了会出安全事故
5. 长期记忆解决"跨会话记住你"，短期记忆（messages）依然要维护好近期上下文——**两者是配合不是替代**
