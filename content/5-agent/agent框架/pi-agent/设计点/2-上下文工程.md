# 设计点 2：上下文工程

> 核心一句话：**上下文是最贵的资源——Pi 的策略是"常驻最小化"（<1000 token 系统提示 + 默认 4 工具），其余全部按需注入（AGENTS.md / Skills / 模板），放不下了就 compaction 压缩**。

## 一、这个设计点解决什么问题

- 每轮发给模型的 prompt 里到底塞什么？（塞多了又贵又慢又淹没重点）
- 项目规则、团队经验怎么进上下文，而不把窗口占满？
- 长会话越滚越大，怎么不爆窗、不失控？

## 二、系统提示词的分层组装

```
┌─────────────────────────────────────────┐
│ 基础系统提示（编码代理人格 + guidelines + 工具片段）│  ← 内核生成，<1000 token
├─────────────────────────────────────────┤
│ AGENTS.md（项目规则，从 cwd 向上遍历自动发现）    │  ← 跟着仓库走
├─────────────────────────────────────────┤
│ SYSTEM.md（稳定行为边界）                       │
├─────────────────────────────────────────┤
│ APPEND_SYSTEM.md（追加指令，~/.pi/agent 或 .pi）│
├─────────────────────────────────────────┤
│ Skills 的 name + description（正文按需加载）    │  ← 只有目录常驻
└─────────────────────────────────────────┘
```

SDK 层全部可覆盖（`DefaultResourceLoader`）：

```typescript
// 完全替换 / 追加（demo 03）
systemPromptOverride: () => "You are...",
appendSystemPromptOverride: (base) => [...base, "## Additional Instructions\n- Be concise"],
// 虚拟注入 AGENTS.md，或禁用自动发现（demo 07 / 12）
agentsFilesOverride: (current) => ({ agentsFiles: [...] })
```

## 三、Skills：按需加载的团队经验

- 遵循开放 Agent Skills 标准：`.pi/skills/<name>/SKILL.md`（frontmatter 写 name + description）
- **只有 name + description 常驻系统提示，正文按需加载**——这是"不占常驻上下文"的关键
- 发现范围：`cwd/.pi/skills`、`~/.pi/agent/skills` 等；SDK 可筛选/合并/替换/内联定义（demo 04 的 `skillsOverride` + `createSyntheticSourceInfo`）
- `disableModelInvocation`：只允许用户手动触发，不许模型自己调

```markdown
---
name: release-checklist
description: 发布前检查流程
---
# 发布检查清单
1. 跑全量测试：npm test
2. 检查 CHANGELOG …
```

## 四、Prompt 模板：文件版斜杠命令

`/templatename` 触发，模板是 markdown 文件（`cwd/.pi/prompts/`、`~/.pi/agent/prompts/`），内容作为 prompt 注入。团队的固定流程（部署步骤、审查清单）沉淀成模板，比每次口述可靠（demo 08）。

## 五、Compaction：长会话压缩

### 5.1 整体流程

```
上下文逼近窗口（threshold 提前压）或已爆窗（overflow 事后压）
  → session_before_compact 扩展钩子（可完全替换摘要逻辑）
  → prepareCompaction()：选切点、收集待摘要消息
  → compact()：LLM 生成结构化摘要（失败不落盘，带重试）
  → 保存 compaction entry（summary + firstKeptEntryId，会话树上可回溯）
  → overflow 场景 willRetry=true：compact 完自动 continue 被打断的 turn
```

### 5.2 双触发路径（`agent-session.js`）

| 路径 | 时机 | 行为 |
|---|---|---|
| **threshold**（提前压） | ① 下一次 assistant 请求前 `_compactBeforeNextAssistantResponse`；② 每次 `agent_end` 后 `_checkCompaction` | `contextTokens > contextWindow - reserveTokens`（默认 `reserveTokens: 16384`）即压，不打断当前轮 |
| **overflow**（事后压） | provider 返回 context overflow 错误，或 `stopReason === "length"` 且可恢复 | compact 后 `continue()` 恢复被打断的 turn；**只重试一次**（`_overflowRecoveryAttempted` 标记），再失败就报错让用户换大窗口模型 |

上下文 token 的估算很务实：优先用最后一次有效响应的真实 `usage.totalTokens`（含 cache 读/写），其后新消息才用 `chars/4` 启发式估算（`estimateContextTokens`）——**能用真实值不靠猜**。

### 5.3 切点选择（`findCutPoint`）

不是简单截断，有三条边界规则：

1. 从最新消息**向前**累计估算 token，凑够 `keepRecentTokens`（默认 20000）处切开——保住最近的完整工作现场
2. 只在合法切点切（user / assistant / bashExecution / custom…），**绝不在 toolResult 处切**——工具结果必须紧跟其调用，否则上下文错乱
3. 切在一轮（turn）中间时（split turn），对该轮前缀单独生成小摘要（"Original Request / Early Progress / Context for Suffix"），拼在主摘要后面——避免保留的"下半场"没头没脑

### 5.4 结构化摘要（`generateSummary`）

被丢弃的消息序列化进 `<conversation>` 标签，用**固定模板**让 LLM 输出 checkpoint：

```
## Goal / ## Constraints & Preferences / ## Progress（Done | In Progress | Blocked）
## Key Decisions / ## Next Steps / ## Critical Context
```

- **增量合并**：已有旧摘要时走 UPDATE prompt——"PRESERVE all existing information"，只做增量更新（把 In Progress 挪到 Done、刷新 Next Steps），多次压缩不会滚雪球丢信息
- **强调保真**：模板硬性要求"Preserve exact file paths, function names, and error messages"
- **文件清单兜底**：从历史工具调用提取 `readFiles` / `modifiedFiles` 附在摘要尾部，存进 entry 的 `details`，下次 compaction 会继承——模型至少知道"我动过哪些文件"

### 5.5 可靠性细节

- 摘要调用复用主对话的重试策略（`retryAssistantCall`），瞬时断流不失败
- `stopReason === "error" | "length"` 的摘要**拒绝落盘**（半截摘要当 checkpoint 是灾难）；摘要里若混入 toolCall 也判失败
- 摘要是独立 LLM 调用，`cacheRetention: "none"`——一次性内容不污染缓存

### 5.6 落盘与重建

**压缩是有损的，日志是无损的**：`.jsonl` 会话文件不删任何条目，只追加一条 `compaction` entry（`summary + firstKeptEntryId`）。重建 LLM 上下文 = 摘要 + `firstKeptEntryId` 之后的条目——随时可以回溯、甚至撤销压缩。

### 5.7 可定制点

```typescript
// 主动压缩：保留什么、丢什么，可以下指令
await session.compact("保留所有架构决策，丢弃中间调试过程");

// 设置里关闭/调参（demo 10）
settingsManager.applyOverrides({
  compaction: { enabled: false }  // 或自定义 reserveTokens / keepRecentTokens
});

// session_before_compact 钩子：返回自定义 summary 即整体替换默认逻辑
// （examples/extensions/custom-compaction.ts，如换 Gemini Flash 做廉价摘要）
// （examples/extensions/handoff.ts：干脆不压缩，把要点写进外置文档开新会话）
```

> 对照自研七层地图的记忆层：这就是"[LLM长期记忆](../../Agent/link_LLM长期记忆原理)摘要压缩"方案的工程化——**双触发 + 结构化 checkpoint + 增量合并 + 无损日志 + 钩子可替换**。

## 六、1/3 上下文效率从哪来

Databricks 基准里 Pi 每轮发送的上下文约为同类工具 1/3，拆开看就是四件事：

1. 系统提示 <1000 token（别家数千）
2. 默认只挂 4 个工具（别家十几个）
3. Skills/知识按需加载，不常驻
4. compaction 主动压长会话

## 七、设计启示（迁移到你自己的 Agent）

1. **常驻最小化、按需注入**——通用原则：进系统提示的每一行都要付"每轮都发"的租金
2. **AGENTS.md 是"项目级 system prompt"**：规则跟着仓库走、随 git 版本化，比散在每个人的口头指令里可靠；对应自研七层地图提示层的"Prompt 版本管理"
3. **Skills 的"目录常驻、正文按需"**：和你自己写的 RAG（[link_RAG](../../Agent/link_RAG)）是同一思想——检索式注入优于全量携带
4. **compaction 触发点**：threshold 提前压（省成本）vs overflow 事后压（保信息），Pi 两者都留了口子
