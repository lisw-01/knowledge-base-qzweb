# 设计点 3：事件系统

> 核心一句话：**循环的每个关键节点都广播事件；TUI 渲染、RPC 转发、扩展拦截、会话持久化、成本统计全部只是订阅者——内核不认识任何一个消费者**。
> 系列：[[0-Pi Agent总览]] ｜ 上一篇 [[2-工具系统]] ｜ 下一篇 [[4-模型适配]] ｜ demo：[01-minimal](../pi-sdk-demo/01-minimal)（订阅流式输出）、[06-extensions](../pi-sdk-demo/06-extensions)（扩展事件）

## 一、这个设计点解决什么问题

一个 Agent 同时要伺候好几种消费者：

| 消费者 | 想要什么 |
|--------|---------|
| 终端 UI | 逐字流式渲染、工具进度 |
| RPC 客户端 | 转发 delta 给远端 |
| 扩展 | 拦截工具调用、改写结果 |
| 会话持久化 | 每条消息落盘 |
| 成本统计 | token/费用记账 |

如果内核挨个调用这些，每加一个功能都要改内核。Pi 的解法：**内核只广播事件，消费者自己订阅**。

## 二、两层事件

### AgentEvent（pi-agent-core，10 种，内核稳定契约）

| 事件 | 发射时机 |
|------|---------|
| `agent_start` / `agent_end` | 一次 run 的开始/结束（end 携带全部 messages） |
| `turn_start` / `turn_end` | 每轮开始/结束（end 携带 message + toolResults） |
| `message_start` / `message_update` / `message_end` | 一条助手消息的开始/流式更新/结束 |
| `tool_execution_start` / `tool_execution_update` / `tool_execution_end` | 工具执行的开始/进度/结束（end 带 isError） |

### AgentSessionEvent（pi-coding-agent 在其上扩展）

`agent_end { willRetry }` ｜ `agent_settled` ｜ `queue_update { steering, followUp }` ｜ `compaction_start/end` ｜ `auto_retry_start/end` ｜ `summarization_retry_*` ｜ `bash_execution_update` ｜ `entry_appended` ｜ `session_info_changed` ｜ `thinking_level_changed`

> 两层设计：core 事件保持极简稳定（跨产品复用），产品层事件按需加（压缩、重试、队列……）。扩展系统订阅的也是这批事件（见 [[7-扩展系统]]）。

## 三、事件驱动带来了什么

```
                        ┌→ TUI：message_update 逐字渲染
                        ├→ RPC：assistant_delta 转发远端
   Agent Loop（广播者） ─┼→ 扩展：tool_call 拦截 / 审计
   agent/turn/message/   ├→ 会话：entry_appended 落盘
   tool_execution_*      ├→ 成本：usage 记账（挂在消息上）
                        └→ 服务器：快照广播给 attached 连接
```

1. **解耦**：内核零改动接入新消费者；TUI / Print / RPC / Server 四种运行模式共用同一事件流
2. **可观测免费**：日志 = 订阅 `message_update`，回放 = 读事件序列——自研七层地图"运营层"的地基
3. **拦截免费**：`tool_call` / `beforeToolCall` 事件就是护栏层插入点
4. **记账免费**：`usage`（input/output/cacheRead/cacheWrite/cost）挂在每条助手消息上，成本统计不需要额外埋点

## 四、订阅代码（SDK 最常用姿势）

```typescript
session.subscribe((event) => {
  switch (event.type) {
    case "message_update":
      if (event.assistantMessageEvent.type === "text_delta") {
        process.stdout.write(event.assistantMessageEvent.delta);   // 逐字输出
      }
      break;
    case "tool_execution_start":
      console.log(`工具: ${event.toolName}`);
      break;
    case "tool_execution_end":
      console.log(`结果: ${event.result}`);
      break;
    case "agent_settled":
      console.log("完成");
      break;
  }
});
await session.prompt("Hello");
```

## 五、流式协议与事件的关系

pi-ai 层先把厂商的流式响应归一化成 `AssistantMessageEvent`（start / text_delta / thinking_delta / toolcall_delta / done / error，每个 delta 都带最新 `partial`），agent 层再把它包装成 `message_update` 广播。**两层事件各管一段：ai 层管"模型吐了什么"，agent 层管"循环走到哪了"**（详见 [[4-模型适配]]）。

## 六、设计启示（迁移到你自己的 Agent）

1. **把 while 循环的关键节点事件化**：turn 开始/结束、消息流式更新、工具开始/结束——就 6~10 种，足够驱动一切
2. **订阅者模式让运行模式可扩展**：同一个循环，接 TUI 是终端产品，接 RPC 是服务，接测试是评测框架
3. **事件粒度选三档**：agent（整个任务）/ turn（一轮）/ message+tool（单条消息、单次执行），再细就淹没消费者了
4. **usage 挂在消息上是妙手**：成本统计从第一天起就免费，不需要事后补埋点
