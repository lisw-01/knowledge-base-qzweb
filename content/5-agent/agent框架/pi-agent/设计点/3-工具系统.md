# 设计点 3：工具系统

> 核心一句话：**工具 = 一个带 JSON Schema 的函数对象；执行 = 固定四阶段流水线（校验/前置钩子 → 执行 → 收尾钩子 → 截断保护）；执行环境（本地 fs / 远程 SSH）通过 Operations 接口整体可插拔**。
> 系列：[[0-Pi Agent总览]] ｜ 对应（2）之③工具层 ｜ 上一篇 [[2-上下文工程]] ｜ 下一篇 [[4-会话系统]] ｜ demo：[05-tools](../pi-sdk-demo/05-tools)、[06-extensions](../pi-sdk-demo/06-extensions)

## 一、这个设计点解决什么问题

| 问题 | 白话版 |
|------|--------|
| 参数能信吗？ | 模型真的会瞎传参数，执行前必须校验 |
| 前后插逻辑插在哪？ | 审计、拦截、改写结果，想在工具执行前后挂钩子 |
| 换执行环境怎么办？ | 同一个 read/write，本地跑和远程（SSH/容器）跑，最好不改业务代码 |
| 长任务进度怎么显示？ | 工具跑半天，UI 得有进度反馈 |
| 工具能叫停 agent 吗？ | "测试全绿"这种结果应该能直接终止任务 |

## 二、AgentTool 类型（pi-agent-core）

```
AgentTool<TParams, TDetails> extends Tool<TParams>:
  name              -- 给模型看的名字
  description       -- 给模型看的说明（模型选错工具 90% 是这里写得烂）
  parameters        -- JSON Schema（typebox）
  label             -- 给 UI 看的人类可读名
  prepareArguments? -- 原始参数兼容垫片
  execute(toolCallId, params, signal?, onUpdate?) -> AgentToolResult<TDetails>
  executionMode?    -- "sequential" | "parallel"

AgentToolResult<T>:
  content: (Text|Image)[]   -- 给模型看的结果
  details: T                -- 给 UI/扩展看的结构化细节
  usage?, addedToolNames?, terminate?   -- terminate: 让整个 agent 停下来
```

关键设计：**一个工具三种视角**——`name/description/parameters` 给模型，`label` 给人，`details` 给 UI。`execute` 的 `signal` 支持中止，`onUpdate` 支持流式进度。

## 三、四阶段执行流水线

```
模型输出 toolCall
   ↓
① Prepare    参数校验 + beforeToolCall 钩子（可阻止 / 可终止整个 run）
   ↓
② Execute    tool.execute()，长任务经 onUpdate 流式回报进度
   ↓
③ Finalize   afterToolCall 钩子（可改写 content / details / isError / terminate）
   ↓
④ 截断保护    stopReason=length 时，所有 tool call 直接标记失败，
             绝不执行可能残缺的参数
```

| 阶段 | 干什么 | 你的插入点 |
|------|--------|-----------|
| 1 Prepare | 校验 + `beforeToolCall` | 拦截 / 审计（安全防线主战场） |
| 2 Execute | `execute()` + `onUpdate` | 工具本体 |
| 3 Finalize | `afterToolCall` | 结果改写 / 脱敏 / 补充记账 |
| 4 截断保护 | 残缺参数直接失败 | 兜底 |

三个插入点的签名速查：

| 插入点 | 签名 | 返回值语义 |
|---|---|---|
| ① `pi.on("tool_call")`（= beforeToolCall） | `(event: { toolName, input })` | `{ block: true, reason }` 阻止执行；`undefined` 放行 |
| ② `execute()` 参数 | `(toolCallId, params, signal?, onUpdate?, ctx?)` | 返回 `AgentToolResult` |
| ③ `pi.on("tool_result")`（= afterToolCall） | `(event: { result })` | 返回新 result 覆盖原结果；`undefined` 原样放行 |

### ① Prepare：执行前的拦截与审计（安全防线主战场）

**应用场景**：危险命令拦截、权限白名单、审计日志、按策略否决或终止整个 run。

**参数含义**：`event.toolName` 即将执行的工具名；`event.input` 模型给出的参数（框架已按 Schema 校验过，但"合法"≠"安全"）；返回 `{ block: true, reason }` 时 `reason` 作为错误结果回喂模型——模型看到的是"被拦截 + 原因"，下一轮自行调整。

```typescript
pi.on("tool_call", async (event) => {
  // event.toolName: 即将执行的工具名
  // event.input:    模型给的参数对象（已过 Schema 校验）
  // 拦截：合法但危险的操作
  if (event.toolName === "bash" && /rm -rf|DROP TABLE/.test(event.input.command)) {
    return { block: true, reason: "危险操作已被企业策略拦截" };   // reason 会回喂给模型
  }
  // 审计：每次调用落盘（谁、在哪个目录、执行了什么）
  auditLog.write({ user: currentUser, tool: event.toolName, input: event.input });
  return undefined;   // 放行
});
```

### ② Execute：工具本体（signal 中止 + onUpdate 进度）

**参数含义**：

| 参数 | 含义 | 必须用吗 |
|---|---|---|
| `toolCallId` | 本次调用唯一 id——结果关联、日志追踪用 | 一般透传 |
| `params` | 已按 JSON Schema 校验的强类型参数 | 必用 |
| `signal` | `AbortSignal`：用户 Esc / `abort()` 时触发——**不接它，长任务停不下来** | 长任务必须接 |
| `onUpdate` | 进度回调：流式回报"跑到哪了"，UI 实时显示 | 长任务用 |
| `ctx` | 调用方环境（扩展上下文） | 按需 |

**返回值 `AgentToolResult`**：`content` 给模型看（Text|Image[]，会进上下文）；`details` 给 UI/扩展看（结构化细节）；`isError` 标记失败（回喂但不重试）；`terminate` 让整个 agent 直接停下来。

**应用场景**：长任务（构建/测试/批量处理）必须接 `signal` + `onUpdate`；"测试全绿就该停"这类确定性终点用 `terminate`，比让模型自己判断更可靠。

```typescript
pi.registerTool({
  name: "run_tests",
  label: "Run Tests",
  description: "运行测试套件",
  parameters: Type.Object({ filter: Type.String() }),
  execute: async (toolCallId, params, signal, onUpdate, _ctx) => {
    const proc = spawn("npm", ["test", "--", params.filter]);
    signal?.addEventListener("abort", () => proc.kill());          // Esc → 杀子进程
    proc.stdout.on("data", (chunk) => onUpdate?.({ message: chunk.toString() }));  // 实时进度
    const code = await new Promise((r) => proc.on("close", r));
    return {
      content: [{ type: "text", text: code === 0 ? "全部通过" : `有失败，退出码 ${code}` }],  // 给模型
      details: { exitCode: code },                                  // 给 UI/扩展
      terminate: code === 0,                                        // 全绿 → 直接叫停 agent
    };
  },
});
```

### ③ Finalize：执行后的改写、脱敏、记账

**应用场景**：敏感信息脱敏（**工具返回 = 模型可见的输入**，进上下文前过滤手机号/密钥）、结果补写、补充记账、识别瞬时错误引导模型重试（→ [[5-Agent循环]] §五路径 2）。

**参数含义**：`event.result` 即 `AgentToolResult`（content / details / isError / terminate）；返回新对象**覆盖**原结果，返回 `undefined` 原样进上下文。

```typescript
pi.on("tool_result", async (event) => {
  // event.result: { content: (Text|Image)[], details, isError, ... }
  // 脱敏：手机号绝不进模型上下文（也顺便不进后续 LLM 请求）
  const masked = event.result.content.map((c) =>
    c.type === "text" ? { type: "text", text: c.text.replace(/\b1[3-9]\d{9}\b/g, "***") } : c
  );
  return { ...event.result, content: masked };   // 返回新对象 → 覆盖；undefined → 原样放行
});
```

### ④ 截断保护：全自动兜底（无干预点）

**应用场景**：模型输出被截断（`stopReason = length`）时，tool call 的参数可能是半截 JSON——`failToolCallsFromTruncatedMessage` 把所有 tool call 直接标记失败，**绝不执行可能残缺的参数**。执行半截参数是事故源，"失败优于残缺执行"（→ [[5-Agent循环]] §四）。

> **工具不是只有一个 `execute()` 吗，哪来的四阶段？**——四阶段流水线不在工具内部，而是**核心循环在 `execute()` 外面套的包装**：工具作者只写业务逻辑（②），校验、钩子调度、兜底都是框架替你跑的（①③④）。`beforeToolCall` / `afterToolCall` 也不是工具的方法，是扩展系统注册的钩子，框架在流水线固定位置回调——一个钩子能管住所有工具。类比 Express middleware 包着 handler、Spring AOP 环绕通知包着业务方法。

> **框架在跑，开发者还需要干预吗？**——框架定**机制**（何时调用），开发者填**策略**（调用什么）。不干预也能跑，干预是可选增强：

| 阶段 | 框架自动做（零干预也能跑） | 开发者可选干预 |
|------|------|------|
| ① Prepare | 按 Schema 校验参数；无钩子则直通 | 写扩展注册 `beforeToolCall`：拦截危险命令、审计、否决 |
| ② Execute | 调度调用、传 `signal`/`onUpdate` | **必须写** `execute()` 本体；决定 `executionMode` |
| ③ Finalize | 无钩子则结果原样进上下文 | 写 `afterToolCall`：脱敏、改写结果、设 `terminate` 叫停 |
| ④ 截断保护 | 全自动，无干预点 | —— |

> 要点：**框架把"在哪干预"定死了，把"是否干预、干预成什么样"留给开发者**。默认裸奔也能跑，生产环境的护栏（拦截/脱敏/审计）仍要自己写扩展补上——干预的单位是"一个扩展管所有工具"，干预点收敛了，而不是消失了。

> before / after 两个钩子 + onUpdate 进度回调，就是自研 Agent 七层地图里**护栏层的标准插入位**（见 [（2）agent开发需要处理的功能点和设计原则](../../Agent/（2）agent开发需要处理的功能点和设计原则)）。

## 四、内置 8 工具与分组

| 工具 | Schema |
|---|---|
| read | `{ path, offset?, limit? }` |
| bash | `{ command, timeout? }` |
| powershell | `{ command, timeout? }` |
| edit | `{ path, edits: [{ oldText, newText }] }` |
| write | `{ path, content }` |
| grep | `{ pattern, path?, include? }` |
| find | `{ pattern, path? }` |
| ls | `{ path? }` |

- **默认只挂 4 个**（read / bash / edit / write），其余按白名单启用——上下文省的秘诀之一
- 工具分组：Coding 默认组（read/bash/edit/write）、只读组（read/grep/find/ls）
- 每个工具有**双重工厂**：`createXxxTool()` 返回 AgentTool（给核心循环），`createXxxToolDefinition()` 返回 ToolDefinition（给扩展渲染/UI）

## 五、Operations：执行环境可插拔

每个工具的落盘/执行动作抽象成接口：`ReadOperations`、`EditOperations`、`BashOperations`……默认是本地 `fs`/`spawn` 实现，可以整体替换成**远程委派**（如 SSH）。

→ 效果：工具的业务逻辑（怎么读、怎么校验、怎么打补丁）与执行环境（在哪执行）彻底解耦。本地 → 容器 → 远程切换零成本，这正是"无沙箱哲学"能成立的前提——隔离交给执行环境，不交给工具代码。

## 六、自定义工具的两种方式

```typescript
// 方式 1：SDK 直传（demo 05）
const { session } = await createAgentSession({
  customTools: [myTool],
  tools: ["read", "bash", "my_tool"],   // 白名单里加上自定义工具名
});

// 方式 2：扩展注册（demo 06，推荐：可拦截、可复用、可分发）
pi.registerTool({
  name: "my_tool",
  label: "My Tool",
  description: "Does something useful",
  parameters: Type.Object({ input: Type.String() }),
  execute: async (_toolCallId, params, _signal, _onUpdate, _ctx) => ({
    content: [{ type: "text", text: `Processed: ${params.input}` }],
    details: {},
  }),
});
```

## 七、设计启示（迁移到你自己的 Agent）

1. **四阶段流水线是通用骨架**：哪怕不用 Pi，也建议把工具执行拆成 prepare / execute / finalize——拦截、审计、脱敏全有了挂点
2. **三种视角分离**：给模型的（name/description/schema）、给人的（label）、给 UI 的（details），别混在一个字符串里
3. **Operations 抽象 = 逻辑与执行环境分离**：做本地工具时顺手留这层接口，之后接沙箱/远程就是换个实现类
4. **terminate 字段**：让工具能主动叫停 agent（"测试全绿，任务完成"），比让模型自己判断更可靠
5. **默认工具宁少勿多**：4 个工具 + 极简 schema 是 Pi 上下文效率的来源之一；工具越多，模型选错率越高
