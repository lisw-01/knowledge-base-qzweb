# 设计点 7：扩展系统

> 核心一句话：**扩展 = 一个导出 `default function (pi: ExtensionAPI)` 的 TypeScript 文件，通过事件钩子改行为、registerTool/registerCommand 加能力；它 import 的 pi-* 依赖由宿主经 virtual modules 注入，不用自带 node_modules**。
> 系列：[[0-Pi Agent总览]] ｜ 上一篇 [[6-会话系统]] ｜ 下一篇 [[8-远程会话栈]] ｜ demo：[06-extensions](../pi-sdk-demo/06-extensions)

## 一、这个设计点解决什么问题

| 问题 | 白话版 |
|------|--------|
| 不改内核加能力 | 加工具、加命令、加快捷键、加 UI 组件 |
| 拦截运行时行为 | 危险命令拦截、审计日志、结果改写 |
| 第三方分发 | 社区扩展装上就能用，别有依赖地狱 |
| 宿主一致性 | 扩展用的 pi API 必须和宿主同版本，不能各自装一份 |

Pi 内核刻意不做 MCP / 子代理 / 权限弹窗——这些全是扩展：`pi install pi-sub-agent` 就有子代理了。**内核极小 + 扩展面全开**是同一枚硬币的两面。

## 二、扩展的形态与发现

三种形态：`Extension`（文件）、`InlineExtension`（代码内联）、`ExtensionFactory`（工厂）。

自动发现位置：

- `~/.pi/agent/extensions/`（全局）
- `<cwd>/.pi/extensions/`（项目级，随 git 走）
- `settings.json` 的 `extensions` 数组（指定路径）
- SDK：`DefaultResourceLoader({ additionalExtensionPaths, extensionFactories })`

社区包：`pi install <package-name>` 一条命令。

## 三、ExtensionAPI：扩展能做什么

```typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  // ① 订阅事件（改行为/拦截）
  pi.on("agent_start", async () => console.log("[Extension] Agent starting"));

  pi.on("tool_call", async (event) => {
    console.log(`[Extension] Tool: ${event.toolName}`);
    return { block: true, reason: "危险操作已被策略拦截" };   // 返回 block 可阻止执行
    // return undefined;  // 放行
  });

  // ② 注册自定义工具
  pi.registerTool({
    name: "my_tool",
    label: "My Tool",
    description: "Does something useful",
    parameters: Type.Object({ input: Type.String() }),
    execute: async (_toolCallId, params, _signal, _onUpdate, _ctx) => ({
      content: [{ type: "text", text: `Processed: ${params.input}` }],
      details: {},
    }),
  });

  // ③ 注册命令（/mycommand）
  pi.registerCommand("mycommand", {
    description: "Do something",
    handler: async (args, ctx) => ctx.ui.notify(`Command executed with: ${args}`),
  });
}
```

可订阅的事件覆盖全生命周期：`session_start / session_shutdown / session_before_switch / session_before_fork / session_before_compact / session_compact / session_tree / agent_start / agent_end / before_agent_start / before_provider_request / tool_call / tool_result / turn_start / turn_end / message_start / message_end / input / context`。

还能注册：CLI flags、UI 组件。

## 四、virtual modules：依赖注入式的加载

`ExtensionRunner` 加载扩展时，把 `pi-agent-core`、`pi-tui`、`pi-ai`、`pi-coding-agent` 等包**作为虚拟模块注入**扩展的 import 环境：

- 扩展 `import { ... } from "@earendil-works/pi-coding-agent"` 拿到的就是宿主运行中的同一份实例
- **扩展零依赖安装**：不用 node_modules，`pi install` 只拉扩展自己的代码
- **版本永远一致**：不存在"扩展用旧版 API、宿主是新版"的漂移

## 五、安全拦截实战（企业必备）

Pi 无沙箱（见 [[9-安全与可观测]]），事件钩子就是自建护栏层的主战场：

```typescript
pi.on("tool_call", async (event) => {
  // 1. 策略拦截
  if (event.toolName === "bash" && /rm -rf|DROP TABLE/.test(event.input)) {
    return { block: true, reason: "危险操作已被企业策略拦截" };
  }
  // 2. 审计日志
  auditLog.write({ user: currentUser, tool: event.toolName, input: event.input });
  return undefined;   // 放行
});
```

## 六、设计启示（迁移到你自己的 Agent）

1. **护栏层插件化**：拦截 / 审计 / 脱敏做成扩展而不是内核功能——内核保持"纯循环"，策略随部署环境换
2. **virtual modules 值得抄**：做任何插件系统都有"插件与宿主共享依赖"问题（版本漂移、重复安装），这是目前见过最干净的解法之一
3. **事件清单即扩展点文档**：把可订阅事件列出来，扩展能力边界一目了然——先设计事件，再设计插件 API
4. **扩展分全局/项目两级**：个人偏好放 `~/.pi`，团队约定放 `<cwd>/.pi` 随 git 走——权限和分发路径天然分开
