# 设计点 6：扩展系统

> 核心一句话：**扩展 = 一个导出 `default function (pi: ExtensionAPI)` 的 TypeScript 文件，通过事件钩子改行为、registerTool/registerCommand 加能力；它 import 的 pi-* 依赖由宿主经 virtual modules 注入，不用自带 node_modules**。
> 系列：[[0-Pi Agent总览]] ｜ 对应（2）之⑥护栏层（插件化路线）｜ 上一篇 [[5-Agent循环]] ｜ 下一篇 [[7-事件系统]] ｜ demo：[06-extensions](../pi-sdk-demo/06-extensions)

## 一、这个设计点解决什么问题

| 问题 | 白话版 |
|------|--------|
| 不改内核加能力 | 加工具、加命令、加快捷键、加 UI 组件 |
| 拦截运行时行为 | 危险命令拦截、审计日志、结果改写 |
| 第三方分发 | 社区扩展装上就能用，别有依赖地狱 |
| 宿主一致性 | 扩展用的 pi API 必须和宿主同版本，不能各自装一份 |

Pi 内核刻意不做 MCP / 子代理 / 权限弹窗——这些全是扩展：`pi install pi-sub-agent` 就有子代理了。**内核极小 + 扩展面全开**是同一枚硬币的两面。

## 二、扩展的形态与发现

三种形态：`Extension`（文件）、`InlineExtension`（代码内联）、`ExtensionFactory`（工厂）。

自动发现位置：

- `~/.pi/agent/extensions/`（全局）
- `<cwd>/.pi/extensions/`（项目级，随 git 走）
- `settings.json` 的 `extensions` 数组（指定路径）
- SDK：`DefaultResourceLoader({ additionalExtensionPaths, extensionFactories })`

社区包：`pi install <package-name>` 一条命令。

## 三、ExtensionAPI：扩展能做什么

```typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  // ① 订阅事件（改行为/拦截）
  pi.on("agent_start", async () => console.log("[Extension] Agent starting"));

  pi.on("tool_call", async (event) => {
    console.log(`[Extension] Tool: ${event.toolName}`);
    return { block: true, reason: "危险操作已被策略拦截" };   // 返回 block 可阻止执行
    // return undefined;  // 放行
  });

  // ② 注册自定义工具
  pi.registerTool({
    name: "my_tool",
    label: "My Tool",
    description: "Does something useful",
    parameters: Type.Object({ input: Type.String() }),
    execute: async (_toolCallId, params, _signal, _onUpdate, _ctx) => ({
      content: [{ type: "text", text: `Processed: ${params.input}` }],
      details: {},
    }),
  });

  // ③ 注册命令（/mycommand）
  pi.registerCommand("mycommand", {
    description: "Do something",
    handler: async (args, ctx) => ctx.ui.notify(`Command executed with: ${args}`),
  });
}
```

可订阅的事件覆盖全生命周期：`session_start / session_shutdown / session_before_switch / session_before_fork / session_before_compact / session_compact / session_tree / agent_start / agent_end / before_agent_start / before_provider_request / tool_call / tool_result / turn_start / turn_end / message_start / message_end / input / context`。

还能注册：CLI flags、UI 组件。

## 四、virtual modules：依赖注入式的加载

### 4.1 先看问题：扩展的 import 由谁满足？

扩展是宿主**运行时**才加载的用户 TS 文件，但它的第一行就是：

```typescript
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
```

按 Node 默认规则，这行会从扩展文件所在位置向上找 `node_modules`——而扩展没有 node_modules，直接 `MODULE_NOT_FOUND`。三种解法：

| 方案 | 做法 | 结果 |
|------|------|------|
| A. peerDependencies | 强迫用户自己装 pi-*，版本还得对齐 | 依赖地狱，装错版本照样崩 |
| B. 扩展自带 node_modules | `pi install` 时把 pi-* 装进扩展目录 | **双实例灾难**（见 4.2） |
| C. virtual modules | 宿主把**自己正在运行的模块实例**直接递给扩展 | ✓ Pi 的选择 |

### 4.2 为什么方案 B 是灾难：双实例问题

如果扩展目录里装了第二份 `pi-coding-agent`：

- 内存里出现**两个**事件总线、两个工具注册表——扩展 `pi.on("tool_call", ...)` 注册到了自己那份上，宿主循环根本看不见，**拦截静默失效**
- `msg instanceof AssistantMessage` 这类判断跨副本全部返回 false
- 版本漂移：扩展锁的是旧版 API，宿主升级后行为不一致

结论：插件和宿主要共享的不是"同一个版本号"，而是**同一个对象**。

### 4.3 实现：jiti + 一张虚拟模块表

Pi 用 [jiti](https://github.com/unjs/jiti)（Nuxt / Tailwind CLI 同款的运行时 TS 加载器）加载扩展，核心是给 jiti 传一张"包名 → 宿主模块实例"的表。源码：`packages/coding-agent/src/core/extensions/virtual-modules.ts`：

```typescript
// virtual-modules.ts（节选，中文注释为笔者所加）
import * as bundledPiAgentCore from "@earendil-works/pi-agent-core";
import * as bundledPiAiCompat from "@earendil-works/pi-ai/compat";
import * as bundledPiTui from "@earendil-works/pi-tui";
import * as bundledTypebox from "typebox";
import * as bundledPiCodingAgent from "../../index.ts";   // ← 宿主自己

export const VIRTUAL_MODULES: Record<string, unknown> = {
  typebox: bundledTypebox,                  // 连 typebox 都代管：
  "@sinclair/typebox": bundledTypebox,      // 扩展里的 Type.Object 也不用装包
  "@earendil-works/pi-agent-core": bundledPiAgentCore,
  "@earendil-works/pi-tui": bundledPiTui,
  "@earendil-works/pi-ai": bundledPiAiCompat,
  "@earendil-works/pi-coding-agent": bundledPiCodingAgent,
  // ...还有 @mariozechner/* 旧 scope 的同名映射，老扩展不用改一行代码
};
```

加载扩展时（`loader.ts` 的 `loadExtensionModule`）：

```typescript
const jiti = createJiti(import.meta.url, {
  moduleCache: false,                       // 不复用模块缓存：每次加载重新求值，支持热重载
  virtualModules: await getVirtualModules(), // ← 解析 import 先查这张表，命中就不碰磁盘
});
const module = await jiti.import(extensionPath, { default: true });
const factory = module as ExtensionFactory; // 即扩展导出的 default function (pi) {...}
```

串起来看一条 import 的旅程：

```
扩展代码: import { Type } from "typebox"
  ↓ jiti 解析时先查 virtualModules 表
  ↓ 命中 → 直接返回宿主静态 import 进来的那个模块对象（完全绕开 node_modules）
  ↓ 未命中（扩展自己的第三方依赖）→ 走 Node 正常解析
```

两个容易忽略的点：

- **`import type` 编译后即被擦除**：`import type { ExtensionAPI }` 在运行时根本不触发加载器，只服务于编辑器类型提示；真正需要虚拟模块的是**值导入**（如 `Type`、pi-tui 组件）
- **虚拟化的不止 pi-\***：typebox 也由宿主代管，所以"只调 API"的扩展就是一个裸 `.ts` 文件

### 4.4 细节：三种运行形态，三种注入方式

`loader.ts` 按 Pi 自身以什么形态运行，选不同解析策略（`loadExtensionModule`）：

| Pi 的运行形态 | 策略 | 为什么 |
|------|------|------|
| 编译为单文件二进制（Bun / Node SEA / bundled Node） | `virtualModules` + `tryNative: false` | 磁盘上根本没有 node_modules，pi-* 只能来自二进制内嵌的宿主模块 |
| 从源码跑（TypeScript） | `virtualModules` + `tsconfigPaths` | 同上，顺带解析 monorepo 的 tsconfig paths |
| 普通安装的 Node 产物（dist） | `alias`：把 pi-* 指到宿主 dist 的真实文件路径 | 不需要虚拟模块——两份 import 解析到**同一个文件**，Node 模块缓存天然保证单实例 |

三种形态殊途同归：**扩展拿到的 pi-\* 永远是宿主正在运行的那一份**。

### 4.5 为什么叫"依赖注入"

- 传统 DI：容器在**构造对象**时，把依赖塞进构造函数参数
- virtual modules：宿主在**解析 import** 时，把依赖塞进模块环境——注入粒度从"实例"升到"模块"，注入时机从"构造"提前到"import 解析"

近亲：webpack `externals`、Vite `resolve.alias`、VS Code 扩展的 `import * as vscode from "vscode"`（这个"包"从不在扩展的 node_modules 里，由扩展宿主运行时提供）。

三个保证（就是把旧版笔记三行展开）：

1. **扩展零依赖安装**：pi-* 和 typebox 都由宿主代管，`pi install` 不需要装 pi-*，没有 node_modules
2. **版本永远一致**：扩展"依赖"的版本物理上就是宿主自己的版本，漂移在机制上不可能发生
3. **单实例**：扩展与宿主共享同一个事件总线、同一个类定义，`instanceof` 和拦截语义全部成立

## 五、安全拦截实战（企业必备）

Pi 无沙箱（见 [[8-安全与可观测]]），事件钩子就是自建护栏层的主战场：

```typescript
pi.on("tool_call", async (event) => {
  // 1. 策略拦截
  if (event.toolName === "bash" && /rm -rf|DROP TABLE/.test(event.input)) {
    return { block: true, reason: "危险操作已被企业策略拦截" };
  }
  // 2. 审计日志
  auditLog.write({ user: currentUser, tool: event.toolName, input: event.input });
  return undefined;   // 放行
});
```

## 六、设计启示（迁移到你自己的 Agent）

1. **护栏层插件化**：拦截 / 审计 / 脱敏做成扩展而不是内核功能——内核保持"纯循环"，策略随部署环境换
2. **virtual modules 值得抄**：做任何插件系统都有"插件与宿主共享依赖"问题（版本漂移、双实例、重复安装）——注意共享的是**同一个对象**，不是同一个版本号。而且实现成本极低：jiti 的 `virtualModules` 选项现成可用，核心就是一张十来行的映射表
3. **事件清单即扩展点文档**：把可订阅事件列出来，扩展能力边界一目了然——先设计事件，再设计插件 API
4. **扩展分全局/项目两级**：个人偏好放 `~/.pi`，团队约定放 `<cwd>/.pi` 随 git 走——权限和分发路径天然分开
