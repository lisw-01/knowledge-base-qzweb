# 设计点 7：事件系统

> 核心一句话：**循环的每个关键节点都广播事件；TUI 渲染、RPC 转发、扩展拦截、会话持久化、成本统计全部只是订阅者——内核不认识任何一个消费者**。
> 系列：[[0-Pi Agent总览]] ｜ 对应（2）之⑦运营层（地基，贯穿各层）｜ 上一篇 [[6-扩展系统]] ｜ 下一篇 [[8-安全与可观测]] ｜ demo：[01-minimal](../pi-sdk-demo/01-minimal)（订阅流式输出）、[06-extensions](../pi-sdk-demo/06-extensions)（扩展事件）

## 一、这个设计点解决什么问题

一个 Agent 同时要伺候好几种消费者：

| 消费者 | 想要什么 |
|--------|---------|
| 终端 UI | 逐字流式渲染、工具进度 |
| RPC 客户端 | 转发 delta 给远端 |
| 扩展 | 拦截工具调用、改写结果 |
| 会话持久化 | 每条消息落盘 |
| 成本统计 | token/费用记账 |

如果内核挨个调用这些，每加一个功能都要改内核。Pi 的解法：**内核只广播事件，消费者自己订阅**。

## 二、两层事件

### AgentEvent（pi-agent-core，10 种，内核稳定契约）

| 事件 | 发射时机 |
|------|---------|
| `agent_start` / `agent_end` | 一次 run 的开始/结束（end 携带全部 messages） |
| `turn_start` / `turn_end` | 每轮开始/结束（end 携带 message + toolResults） |
| `message_start` / `message_update` / `message_end` | 一条助手消息的开始/流式更新/结束 |
| `tool_execution_start` / `tool_execution_update` / `tool_execution_end` | 工具执行的开始/进度/结束（end 带 isError） |

### AgentSessionEvent（pi-coding-agent 在其上扩展）

`agent_end { willRetry }` ｜ `agent_settled` ｜ `queue_update { steering, followUp }` ｜ `compaction_start/end` ｜ `auto_retry_start/end` ｜ `summarization_retry_*` ｜ `bash_execution_update` ｜ `entry_appended` ｜ `session_info_changed` ｜ `thinking_level_changed`

> 两层设计：core 事件保持极简稳定（跨产品复用），产品层事件按需加（压缩、重试、队列……）。扩展系统订阅的也是这批事件（见 [[6-扩展系统]]）。

### 发射时机：结合 Agent Loop 看两层事件什么时候发（循环骨架 → [[5-Agent循环]] §二）

● = AgentEvent（core）｜ ○ = AgentSessionEvent（产品层）

```
外层 while（续跑）
│
├─ ● agent_start ─────────────── run 开始，广播一次
│
│  内层 while（每个 turn）
│  ├─ ● turn_start ───────────── 每轮开始
│  │
│  ├─ ② 队列注入（steering / followUp）
│  │    └─ ○ queue_update ────── 消息进队时就发（不是 drain 时），
│  │                              UI 实时显示"排队中有 2 条"
│  ├─ ③ streamAssistantResponse（调模型）
│  │    ├─ ● message_start ───── 助手消息开始
│  │    ├─ ● message_update × N ─ 每个流式 delta 一次，
│  │    │      内层 AssistantMessageEvent（text_delta/thinking_delta/toolcall_ delta）原样携带
│  │    │      ○ auto_retry_start/end ─ LLM 调用失败、自动重试期间
│  │    └─ ● message_end ─────── 消息结束（stopReason 定型）
│  │
│  ├─ ④ 工具段（每个 toolCall）
│  │    ├─ ● tool_execution_start ── 开始执行（toolCallId/toolName/args）
│  │    ├─ ● tool_execution_update × N ─ 长任务进度（工具调 onUpdate 才发）
│  │    │      ○ bash_execution_update ─ bash 工具的专项进度
│  │    └─ ● tool_execution_end ── 执行结束，result + isError（成败都发）
│  │
│  └─ ● turn_end ──────────────── 每轮结束（携带 message + toolResults）
│
├─ ● agent_end ───────────────── run 结束（core 版携带全部 messages）
│      ○ Session 版带 { willRetry } ─ 告诉消费者"马上还要自动重试吗"
│      ○ agent_settled ────────── 运行 + 监听器全部沉淀后（waitForIdle 语义）
│
│  （循环外、按需触发）
│  ○ compaction_start/end ────── 上下文压缩前后
│  ○ summarization_retry_* ───── 分支摘要重试期间
│  ○ entry_appended ──────────── 持久化层每追加一条 entry
│  ○ session_info_changed / thinking_level_changed ── 会话属性变更
```

事件 → 循环位置 → 触发条件对照：

| 事件 | 循环位置 | 触发条件 |
|---|---|---|
| `agent_start` / `agent_end` | 外层 while 外侧 | 一次 run 的首尾 |
| `turn_start` / `turn_end` | 内层 while 首尾 | 每个 turn 一次 |
| `message_start` / `message_end` | ③ 内部 | 一条助手消息的首尾（一个 turn 一条） |
| `message_update` | ③ 内部 | **每个流式 delta 一次**——流式最小粒度 |
| `tool_execution_start` / `end` | ④ 内部 | 每个工具调用首尾，成败都发（end 带 isError） |
| `tool_execution_update` | ② execute 内部 | 工具调 `onUpdate` 才发，不调就没有 |
| `queue_update` | 不在循环里 | **进队时**发（steer/followUp 入队），drain 在 turn 边界 |

四个关键理解点：

1. **粒度四档**：run（agent_*）→ turn（turn_*）→ message（message_*）→ execution（tool_execution_*）——循环走到哪，事件落在哪一档
2. **message_* 三件套是信封**：`message_update` 原样携带 pi-ai 层的 `AssistantMessageEvent`，循环不改写只套壳（见下节）
3. **`tool_execution_*` 没有内层对应物**：工具执行发生在 agent 层，模型层不知道——`toolcall_delta`（模型正在输出调用参数，③）和 `tool_execution_*`（框架真的在执行，④）是两码事
4. **钩子不是事件**：`beforeToolCall` / `shouldStopAfterTurn` 是"循环停下来等返回值"的回调，不在广播序列里——事件给旁观者，钩子给参与者




## 三、流式协议与事件的关系

pi-ai 层先把厂商的流式响应归一化成 `AssistantMessageEvent`（start / text_delta / thinking_delta / toolcall_delta / done / error，每个 delta 都带最新 `partial`），agent 层再把它包装成 `message_update` 广播。**两层事件各管一段：ai 层管"模型吐了什么"，agent 层管"循环走到哪了"**（详见 [[1-模型适配]]）。

> **两层是包装/转发关系，不是两套平行词表**——第四节的订阅代码就是证据：先 switch 外层 `event.type`（AgentEvent），再读内层 `event.assistantMessageEvent.type`。

**1. 内层事件被原样嵌入外层事件转发**

```
pi-ai 层（AssistantMessageEvent）            pi-agent-core 层（AgentEvent）
  { type:"start" }                ──包装──→   message_start
  { type:"text_delta", delta }    ──包装──→   message_update { assistantMessageEvent: ↑原样携带 }
  { type:"toolcall_delta" }       ──包装──→   message_update { assistantMessageEvent: ↑ }
  { type:"done", message }        ──包装──→   message_end { message }
```

即：10 种 core 事件里的 `message_start / message_update / message_end` 三件套，就是 AssistantMessageEvent 流的**信封**——agent 层不改写内容，只套壳广播。

**2. 职责边界**

|       | AssistantMessageEvent（内层）  | AgentEvent（外层）               |
| ----- | -------------------------- | ---------------------------- |
| 产地    | pi-ai，各厂商适配器产出             | pi-agent-core，主循环广播          |
| 回答的问题 | "模型吐了什么"（文本/思考/工具调用**参数**） | "循环走到哪了"（run/turn/消息/工具执行）   |
| 生命周期  | 只存在于**一条助手消息**的生成期间        | 覆盖**整个 run**（多轮、多条消息、多次工具执行） |

**3. 不对称的地方（关键）**

- `toolcall_delta` 只是"模型在输出调用参数"；而 `tool_execution_start/update/end` 是"框架真的在执行工具"——后者**没有**对应的内层事件，因为执行发生在 agent 层，模型层根本不知道
- `turn_start/turn_end`、`agent_start/agent_end` 纯属编排语义，ai 层无对应物
- 反过来 `thinking_delta` 只存在于内层，外层不单独设事件，统一走 `message_update`

> 一句话：**AssistantMessageEvent 是原料流（一条消息一份），AgentEvent 是产品流（一个 run 一份）；message_* 三件套是原料的转发通道，其余 core 事件是编排层自己的节点**。







## 四、事件驱动带来了什么

```
                        ┌→ TUI：message_update 逐字渲染
                        ├→ RPC：assistant_delta 转发远端
   Agent Loop（广播者） ─┼→ 扩展：tool_call 拦截 / 审计
   agent/turn/message/   ├→ 会话：entry_appended 落盘
   tool_execution_*      ├→ 成本：usage 记账（挂在消息上）
                        └→ 服务器：快照广播给 attached 连接
```

1. **解耦**：内核零改动接入新消费者；TUI / Print / RPC / Server 四种运行模式共用同一事件流
2. **可观测免费**：日志 = 订阅 `message_update`，回放 = 读事件序列——自研七层地图"运营层"的地基
3. **拦截免费**：`tool_call` / `beforeToolCall` 事件就是护栏层插入点
4. **记账免费**：`usage`（input/output/cacheRead/cacheWrite/cost）挂在每条助手消息上，成本统计不需要额外埋点

## 五、订阅代码（SDK 最常用姿势）

```typescript
session.subscribe((event) => {
  switch (event.type) {
    case "message_update":
      if (event.assistantMessageEvent.type === "text_delta") {
        process.stdout.write(event.assistantMessageEvent.delta);   // 逐字输出
      }
      break;
    case "tool_execution_start":
      console.log(`工具: ${event.toolName}`);
      break;
    case "tool_execution_end":
      console.log(`结果: ${event.result}`);
      break;
    case "agent_settled":
      console.log("完成");
      break;
  }
});
await session.prompt("Hello");
```


## 六、设计启示（迁移到你自己的 Agent）

1. **把 while 循环的关键节点事件化**：turn 开始/结束、消息流式更新、工具开始/结束——就 6~10 种，足够驱动一切
2. **订阅者模式让运行模式可扩展**：同一个循环，接 TUI 是终端产品，接 RPC 是服务，接测试是评测框架
3. **事件粒度选三档**：agent（整个任务）/ turn（一轮）/ message+tool（单条消息、单次执行），再细就淹没消费者了
4. **usage 挂在消息上是妙手**：成本统计从第一天起就免费，不需要事后补埋点
