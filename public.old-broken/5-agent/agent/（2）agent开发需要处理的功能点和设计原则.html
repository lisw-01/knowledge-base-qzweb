（2）agent开发需要处理的功能点和设计原则

（2）agent开发需要处理的功能点和设计原则

Oct 10, 202612 min read

核心一句话：Agent 的核心代码就一个 while 循环，真正的开发量全在循环之外的工程问题——功能点清单回答”要写什么”，设计原则回答”怎么写不翻车”。
上一篇：（1）agent开发学习路径（怎么学）；本篇：开发 Agent 具体要处理哪些功能点、遵循哪些设计原则。

一、功能点全景：七层地图

不管用什么框架，一个 Agent 系统剥掉外壳，要处理的功能点就这七层（自下而上搭）：

⑦ 运营层：日志 · 追踪 · 成本 · 评估       —— 出了问题怎么查、花了多少钱
⑥ 护栏层：权限 · 确认 · 容错 · 限额       —— 出了事怎么兜住
⑤ 控制层：循环 · 终止 · 规划              —— 流程怎么走、什么时候停
④ 记忆层：短期上下文 · 长期记忆           —— 记住什么、忘掉什么
③ 工具层：注册 · 校验 · 执行 · 错误回喂    —— 真正干活的地方
② 提示层：system · 工具描述 · 格式约束    —— 怎么"指挥"模型
① 模型层：LLM 调用 · 重试 · 流式          —— 地基，上面六层都压在它身上
  • ①~⑤ = 把 Agent 搭起来（构建期），⑥~⑦ = 让它别出事、出事能查（运行期）
  • 分层的意义：换模型只动①，加工具只动③，改流程只动⑤——各层独立演进，互不牵连

二、逐层拆解：每层要处理什么

① 模型层 —— 地基

  • LLM 调用封装：起步只要 chat() / embed() 两个函数
  • 密钥管理：key 放 .env，绝不硬编码进代码、绝不提交 git
  • 超时 + 重试：网络抖动、429 限流是家常便饭，指数退避重试 2~3 次
  • 流式输出：长回答别让用户干等
  • 多模型分工（进阶）：便宜模型干提取/摘要，强模型干决策

关键决策：先锁定一个模型跑通，再谈多模型。把调用封装成一层的意义就是：换模型不改业务代码。

② 提示层 —— 说明书

  • System Prompt 四要素：角色（你是谁）、目标（干什么）、边界（不许干什么）、输出格式（怎么答）
  • 工具描述三件套：name + description + 参数 JSON Schema，写给”没看过你代码的模型”看
  • 格式约束：手写 ReAct 约定格式，或 Function Calling 结构化输出
  • Few-shot 示例：格式总出错时，给 1~2 个示例比讲十句规则都管用
  • Prompt 版本管理：改 prompt = 改代码，留档、可回滚、可对比

模型选错工具、输出格式崩，90% 的锅在提示层——description 就是给模型看的 API 文档。

③ 工具层 —— 手脚

  • 工具注册：注册表（名字 → 函数 + schema），统一入口
  • 参数校验：模型给的参数先验证再执行（类型/范围），它真的会瞎传
  • 结果回填：执行结果作为 Observation 拼回 messages
  • 错误回喂：工具抛错别让程序崩，把报错给模型让它自己调整：
  • 失败分类、有界重试、熔断兜底的完整展开 → （3）ReAct工具调用失败处理
  • 粒度设计：小而专（search_order + refund_order）优于大而全（handle_anything）
  • 幂等性：同一个调用重试一次，不该重复扣款、重复发消息
  • 返回值精简：截断长文本、只回必要字段——工具返回是下一轮的模型输入，又长又臭会撑爆上下文

④ 记忆层 —— 上下文

  • 短期：messages 拼装规则（system + 历史 + 本轮）、超窗裁剪/摘要压缩
  • 上下文膨胀的大头：多轮工具调用后，messages 里涨最快的不是聊天记录，而是工具返回
  • 长期（进阶）：写入时机（会话结束总结 / 每轮提取）、检索 topK、去重合并；原理见 LLM长期记忆原理，存储选型见 向量库，知识库问答见 RAG

一句话口诀：近期带原文，远期压摘要，事实存卡片，知识进向量库。

⑤ 控制层 —— 流程

  • 主循环：while → 调模型 → 解析 Action → 执行 → 拼回 Observation（阶段 1 那个循环）
  • 终止条件四个都要有：
    1. 模型输出 Answer（正常结束）
    2. 最大轮数（防死循环）
    3. 超时（防卡死）
    4. token 预算（防烧钱）
  • 规划：简单任务直接干；复杂任务先让模型列计划、再逐步执行（别过度设计）
  • 中断恢复（进阶）：长任务存检查点，挂了能续跑

终止条件是保险丝：没有最大轮数兜底的 Agent，一次死循环就能烧掉一个月的 token 预算。

⑥ 护栏层 —— 安全网

  • 解析兜底：模型输出不合格式 → 把报错喂回去让它重出，重试 2 次仍失败就人工接管
  • 危险操作确认：删除 / 支付 / 对外发消息，执行前必须人工点一下
  • 权限白名单：工具能碰的目录、数据表、URL 提前列好，白名单外一律拒绝
  • 限额：单任务最大轮数、最大 token、调用频率
  • 脱敏：工具返回的内容进模型前过滤敏感字段（密钥、手机号）

信任要分两个方向看：工具返回 = 模型可见的输入（别喂敏感信息进去）；模型输出 = 不可信数据（先校验再执行）。

⑦ 运营层 —— 仪表盘

  • 日志：每轮 Thought / Action / Observation 落盘——调试 Agent 的唯一靠山
  • 追踪：一个 trace_id 串起一次任务的所有 LLM / 工具调用
  • 成本：记录每次 token 用量，算出”单任务成本”，知道一次对话花几毛钱
  • 评估：攒一组固定测试问题，每次改 prompt / 换模型后回归跑一遍，防止按下葫芦浮起瓢

没有日志的 Agent 是黑盒中的黑盒：出了问题，你连它”当时是怎么想的”都不知道。

三、设计原则（十条）

#原则一句话解释违背的下场
1能用固定流程就不上自主循环步骤确定 → 写死 workflow；要”见机行事”才给模型自主权简单任务硬上 Agent：更贵、更慢、更不可控
2控制流在代码，判断在模型分支/循环/重试用 Python 写死，模型只判断”调哪个工具、传什么参数”把流程逻辑写进 prompt：一改就崩、没法调试
3模型输出 = 不可信输入解析前一律校验格式、类型、范围模型幻觉出一个参数，工具照单全收直接出事故
4工具小而专，描述大于实现一个工具干一件事，description 当 API 文档写大杂烩工具：模型不会用、用错、不敢用
5确定性优先temperature=0、结构化输出同一任务时好时坏，问题无法复现
6失败要回喂，不要吞错误信息拼回上下文，让模型自救程序直接崩，或模型反复踩同一个坑
7高风险必过人写操作默认要人工确认Agent 自作主张删库、付款、群发消息
8可观测先行先加日志，再调 prompt出了问题全靠猜
9token 是钱，上下文是预算及时摘要压缩，工具返回精简成本失控、窗口爆掉、重点被淹没
10从最简单的开始单 Agent + 2 个工具 + 一个循环，按需加复杂度一上来就多 Agent 编排：永远在 debug 框架

前 3 条是架构级的（决定项目成败），后 7 条是工程习惯级的（决定维护成本）。

五、上线前自查清单

  • 有最大轮数 / token 上限兜底（防死循环烧钱）
  • 工具报错不会崩程序（错误回喂给模型）
  • 模型输出先校验再执行（格式、类型、范围）
  • 危险操作有人工确认（删除、支付、对外发消息）
  • 每轮 Thought / Action / Observation 有日志可回放
  • key 不在代码里，prompt 不散落在业务代码里
  • 有固定测试问题集，改动后能回归

全部打勾，才算从”能跑的 demo”变成”敢给别人用的 Agent”。
