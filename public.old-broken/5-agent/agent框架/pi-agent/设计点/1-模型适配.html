设计点 1：模型适配层（pi-ai）

核心一句话：一套统一类型 + 一个归一化流式事件协议 + 逐项 compat 开关 + never-throw 契约，把约 40 家厂商 300+ 模型抹平成一个 stream() 调用——上层循环完全不知道底下是哪家模型。
系列：0-Pi Agent总览 ｜ 对应（2）之①模型层 ｜ 系列首篇 ｜ 下一篇 2-上下文工程 ｜ 实战配置：1-Pi Agent简介 §2.3（models.json 接智谱）｜ demo：02-custom-model、09-api-keys

一、这个设计点解决什么问题

  • 消息格式、流式事件、工具调用结构，OpenAI / Anthropic / Google 各不相同，还有 10 种 wire 格式
  • “OpenAI 兼容”服务各有各的残缺：不支持 developer 角色、不支持 reasoning_effort、流里不带 usage……
  • 上层 agent 循环不想关心这些，更不想为换模型改代码

二、统一类型（types.ts）

Model<TApi>     -- id, name, api, provider, baseUrl, reasoning, cost, contextWindow,
                   maxTokens, thinkingLevelMap, input, samplingParams, headers, compat
Context         -- systemPrompt?, messages: Message[], tools?: Tool[]
Tool<TParams>   -- name, description, parameters (TSchema)
Message         -- UserMessage | AssistantMessage | ToolResultMessage
Usage           -- input, output, cacheRead, cacheWrite, reasoning?, totalTokens, cost
StopReason      -- "pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred"
  • KnownApi 10 种 wire 格式：openai-completions / openai-responses / azure / codex / anthropic-messages / bedrock / google-generative-ai / google-vertex / mistral / pi-messages
  • KnownProvider 约 40 家，models.generated.ts 是脚本生成的模型目录（含成本/窗口/思考等级，禁止手改）

三、归一化流式协议（AssistantMessageEvent）

{ type: "start", partial }                        -- 首事件
{ type: "text_start / text_delta / text_end" }
{ type: "thinking_start / thinking_delta / thinking_end" }
{ type: "toolcall_start / toolcall_delta / toolcall_end" }
{ type: "done", reason, message }
{ type: "error", reason, error }

关键设计：每个 delta 事件都携带最新 partial（完整部分消息）——消费者不需要自己拼状态，拿任何一个事件都是自洽的快照。

type 具体是怎么归一化的

归一化发生在每个 wire 格式（KnownApi）各自的适配器内部：所有适配器实现同一个 ProviderStreams.stream() 契约，把厂商原始 SSE 事件翻译成上面这套统一词表。

1. 按内容类别映射（以 anthropic-messages 为例）

厂商原始事件归一化后
message_startstart（携带空 partial）
content_block_start（text / thinking / tool_use 块）text_start / thinking_start / toolcall_start
content_block_delta（text_delta / thinking_delta / input_json_delta）对应的 *_delta
content_block_stop对应的 *_end
message_delta 的 stop_reasondone，reason 归一化（见 3）
异常 / 中断error（reason: error / aborted）

2. 没有边界语义的厂商，适配器”合成”边界事件

openai-completions 的 chunk 流没有 content_block 概念，适配器自己补：首次收到 delta.content 补发 text_start，finish 时补发 text_end；delta.tool_calls[].function.arguments 用 index 映射成 contentIndex 的 toolcall_*；DeepSeek 式 reasoning_content 映射成 thinking_*。

3. 终止原因归一化成枚举

厂商的 finish 语义全部折叠进 done.reason 四种值：end_turn/stop→stop，max_tokens/length→length，tool_use/tool_calls→toolUse，另有 deferred。加上 error 事件里的 error/aborted，构成 StopReason 全集。

4. 两个配套设计保证归一化可靠

  • partial 快照：累积状态由适配器维护（往 AssistantMessage.content 追加 Text/Thinking/ToolCall），归一化不只是改名，还统一了状态模型
  • compat 开关控制解析行为（见下节）：supportsUsageInStreaming: false 就不解析流中 usage，supportsFinishReason: false 就忽略 finish_reason——同一套归一化逻辑靠开关适配残缺的”OpenAI 兼容”服务
  • never-throw：解析错误、SDK 加载失败、网络错误一律不抛，编码成流上的 error 事件（见第五节）

四、compat 开关：接任何 OpenAI 兼容服务的排查表

开关关掉后 Pi 的行为
supportsDeveloperRole: false改用 system 消息发系统提示
supportsReasoningEffort: false不发 reasoning_effort 参数
supportsStore / supportsUsageInStreaming / supportsFinishReason对应能力不发/不解析
maxTokensField换 max tokens 字段名
requiresToolResultName / requiresAssistantAfterToolResult补发工具结果所需的字段/消息
  • 默认按 baseUrl 自动探测；国产服务（智谱、Ollama、vLLM）常需手动关前两项，否则报错
  • 完全自定义厂商：~/.pi/agent/models.json 写 provider + baseUrl + api + models 即可接入，完整实战见 1-Pi Agent简介 §2.3

五、never-throw 契约 + 懒加载

  • never-throw：StreamFn 一旦调用，请求/模型/运行时的任何失败都必须编码进返回流的 error 事件（stopReason = error/aborted + errorMessage），不允许同步抛出
    → 上层循环不需要 try/catch，错误和正常数据走同一条管道，事件消费者统一处理
  • 懒加载：lazyApi(() => import(...)) 把每家 SDK 包成 ProviderStreams，首次调用才动态加载——不用 Claude 就不加载 Anthropic SDK，启动快、体积省

六、四级鉴权（优先级从高到低）

  1. --api-key 命令行参数（仅内存，不落盘）
  2. ~/.pi/agent/auth.json（OAuth 登录态也存这）
  3. 环境变量（ANTHROPIC_API_KEY 等）
  4. models.json 里 provider 的 apiKey（$ENV_VAR 引用）

SDK 侧对应 modelRuntime.setRuntimeApiKey("anthropic", key) 运行时注入（demo 09）。

七、设计启示（迁移到你自己的 Agent）

  1. 适配层的产出物就两个：统一类型 + 归一化事件流。这两个定好了，上层（循环/UI/扩展）就稳了——先定契约再写适配器
  2. compat 开关清单 = 多厂商兼容排查表：自己接 OpenAI 兼容服务时，逐项过一遍这 8 个开关，能省掉大半调试时间
  3. never-throw 值得抄：把异常塞进数据流，消费者用同一套逻辑处理成败，循环代码干净一个量级
  4. 对照自研七层地图的模型层（见 （2）agent开发需要处理的功能点和设计原则）：Pi 这一层 = 调用封装 + 多模型分工 + 密钥管理的完整参考实现
