设计点 8：安全与可观测

核心一句话：Pi 的安全哲学是”内核不管安全”——以启动用户完整权限运行、无弹窗无沙箱，把安全外置给容器隔离 + 扩展钩子拦截 + 工具白名单三道防线；可观测则靠 usage 记账 + telemetry + evals。
系列：0-Pi Agent总览 ｜ 对应（2）之⑥护栏层＋⑦运营层（综合实践）｜ 上一篇 7-事件系统 ｜ 下一篇 9-远程会话栈 ｜ 企业落地详解：3-Pi Agent分析 第二部分

一、先理解 Pi 的安全哲学（再决定骂不骂它）

Pi 官网的态度：“没有权限确认弹窗——跑在容器里就好”。为什么敢这么设计：

  1. 内核做权限 = 复杂度爆炸：弹窗、策略引擎、沙箱全进内核，直接违背”418 行循环”的极简哲学
  2. 容器/VM 是更硬的隔离：应用层权限弹窗防不住供应链攻击和提示注入，操作系统级隔离防得住
  3. 钩子给了完全的拦截能力：企业可以用扩展自建任意细粒度的策略（见 6-扩展系统 §5）

代价：不懂容器化的用户裸奔有真实风险。所以上生产必须走下面的三道防线，一道不能少。

二、三道防线

防线 1：环境隔离（最硬）

容器化（Docker）/ 权限最小化 / 网络策略——官方推荐的生产姿势。

防线 2：钩子拦截（最灵活）

防线 3：工具白名单（最简单）

对照自研七层地图的护栏层（危险操作确认 / 权限白名单 / 限额 / 脱敏）：Pi 把这四项全部外置成了”容器 + 扩展 + 白名单”的组合，能力不缺，但要自己组装。

三、可观测：记账从第一天就免费

  • usage 挂在每条助手消息上：input / output / cacheRead / cacheWrite / cost——不需要额外埋点，订阅事件流就能建监控面板
  • TUI 底部实时显示当前模型、思考级别、token 消耗、费用估算
  • telemetry 包：TelemetryContext / TelemetrySpan 抽象（span 携带 attributes/events/status）+ 内存参考实现，供 ai/agent 层记录请求链路——厂商中立，可以接到自己的观测后端
  • SDK 模式按用户/项目/任务维度自建统计；compact() 控制长会话成本

四、evals：Agent 的回归测试

evals 包：创建隔离 workspace + agent session → 执行 prompt 步骤 → 收集 transcript、token usage 与成本 → 支持 baseline/candidate 对比与 harness table 生成。

改 prompt / 换模型 / 升级版本后跑一遍固定任务集，防止”按下葫芦浮起瓢”。这正是自研七层地图运营层”评估”项的参考实现。

五、企业级架构参考

+---------------------------------------------+
|  企业入口层：Web UI / 内部平台 / CI / IM 机器人    |
+---------------------------------------------+
|  网关层（可选）：认证鉴权 / 多渠道 / 路由           |
+---------------------------------------------+
|  Pi Agent 层（SDK 内嵌 createAgentSession）      |
|  |- customTools：工单/Jenkins/监控查询           |
|  |- 事件钩子：审计日志 + 危险操作拦截             |
|  |- Skills：团队流程（发布/迁移/排障）            |
|  |- SessionManager：会话持久化（企业存储）         |
+---------------------------------------------+
|  模型层（pi-ai）：云端按任务路由 + 本地敏感数据不出域 |
+---------------------------------------------+
|  执行环境层：容器隔离 / 权限最小化 / 网络策略        |
+---------------------------------------------+

四个关键决策：模型路由（敏感用本地、日常用云）、安全边界（必须容器 + 钩子二次拦截）、会话资产（JSONL + 树，可回放共享复盘）、上下文工程（AGENTS.md + compact + Skills 按需）。

六、设计启示（迁移到你自己的 Agent）

  1. “安全外置”不等于”安全不做”：用 Pi 上生产，三道防线一道不能少；自研时则要想清楚——你的用户有没有能力自己组装防线？没有就得内置
  2. 成本观测从第一天就要有：Pi 把 usage 塞进消息设计，记账零成本——自研时把 usage 放进消息结构而不是日志，统计会顺很多
  3. evals 思路：Agent 的”单元测试” = 固定任务集 + 结果/成本双指标对比，框架升级前后各跑一遍
  4. 对照自研七层地图：本篇 = 护栏层 + 运营层的完整对照，Pi 用”极简内核 + 外置防线”给出了和”内置防线”（Claude Code 弹窗）相反的另一种答案——两种路线的取舍取决于你的用户是谁
