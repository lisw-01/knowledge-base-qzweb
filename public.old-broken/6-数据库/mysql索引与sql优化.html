MySQL索引与SQL优化

MySQL索引与SQL优化

Oct 19, 20266 min read

一句话：索引就是把某一列（或几列）额外排好序存一份，让查找从”全表逐行扫”变成”按结构快速定位”——MySQL InnoDB 默认用 B+ 树。

一、为什么是 B+ 树

结构问题
哈希表等值查询 O(1) 很快，但不支持范围查询和排序（WHERE a > 10 废掉）
二叉/红黑树数据量大时树太高（一亿数据 → 几十层），每层都是一次磁盘 IO
B+ 树矮胖（千万数据约 34 层 = 34 次磁盘 IO）；非叶子节点只存键（一页能塞更多键，更矮）；叶子节点串成有序链表（范围查询顺着链表走）

二、聚簇索引 vs 二级索引（回表）

InnoDB 的表本身就是按主键组织的 聚簇索引（叶子节点存整行数据）：

聚簇索引（主键 id）          二级索引（name 列）
  [30|60|90]                  ['bob'|'kim'|'tom']
   /   |   \                   /    |    \
 叶子: 完整行数据            叶子: 只存 name + 主键 id
  • 通过二级索引查 SELECT * FROM user WHERE name='bob'：
    1. 先在 name 的 B+ 树里找到 bob → 拿到主键 id=7
    2. 再回到聚簇索引按 id 查整行 ← 这一步叫”回表”
  • 覆盖索引：如果要查的列二级索引里都有（如 SELECT id, name FROM ... WHERE name='bob'），不用回表，EXPLAIN 的 Extra 会显示 Using index

三、联合索引与最左前缀原则

联合索引 (a, b, c) 相当于建了 (a)、(a,b)、(a,b,c) 三个索引，排序规则是先按 a 排，a 相同再按 b，依次类推（像字典：先按第一个字母排）。

所以：

索引 (a, b, c)
WHERE a=1              ✅ 走索引
WHERE a=1 AND b=2      ✅
WHERE a=1 AND b=2 AND c=3 ✅
WHERE b=2              ❌ 不走（跳过了 a，相当于字典不看第一个字母）
WHERE a=1 AND c=3      ⚠️ 只有 a 走索引，c 用不上（中间断了 b）
WHERE a>1 AND b=2      ⚠️ a 走范围后，b 不再走索引（a 是范围匹配时后面的列失效）

建索引顺序口诀：等值查询的列放前面，范围查询的列放最后。

四、索引失效的常见场景

写法为什么失效
WHERE YEAR(create_time)=2024对索引列用函数/运算：排序结构对不上计算后的值
WHERE create_time >= '2024-01-01' AND < '2025-01-01'✅ 正确改法：改成范围
WHERE phone = 13800001111（phone 是 varchar）隐式类型转换：MySQL 把列转成数字再比，等于对列套函数
WHERE name LIKE '%三'前缀通配：不知道开头就没法按序定位；'张%' ✅ 可以走
WHERE a=1 OR b=2（b 无索引）or 里有一列没索引 → 全表扫；两列都有索引则可走 index merge
WHERE name != 'x' / NOT IN / IS NOT NULL反向条件命中行太多，优化器判定不如全表扫

本质只有一条：索引 = 预排序 + 按序定位。任何让”有序定位”失效的写法（函数、类型转换、前缀模糊、断裂的最左前缀）都不走索引。

五、EXPLAIN：拿到执行计划再说

重点看四列：

列关注点
type访问类型，好→差：const > ref > range > index（扫全索引）> ALL（全表扫），上线 SQL 至少 range
key实际用到的索引（NULL = 没走索引）
rows预估扫描行数，数量级越大越危险
ExtraUsing index（覆盖索引，好）；Using filesort（额外排序，需要优化）；Using temporary（临时表，警惕）

六、实战优化清单

  1. 选择性差的列别单独建索引：性别、状态这种两三个值的列，索引价值极低（优化器大概率不用）
  2. SELECT * 改具体列：有机会命中覆盖索引，省掉回表
  3. 深分页优化：LIMIT 1000000, 20 要先扫过 100 万行
  4. 索引不是越多越好：每个索引都是一棵要维护的 B+ 树，写入（insert/update/delete）时全都要同步维护，还占空间
  5. 字符串太长用前缀索引：INDEX(name(20))，用 COUNT(DISTINCT LEFT(name, n))/COUNT(*) 找区分度够用的最短前缀
  6. 更新频繁的列慎建索引：主键尽量用自增/有序（避免页分裂，这也是”为什么推荐自增主键”的原因）
